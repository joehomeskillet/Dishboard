Dishboard führt Küchenplanung, Freigabe und Ausgabe in einer Flask-/PostgreSQL-Anwendung zusammen — mit strikt getrennten Kanälen für Patienten und Cafeteria. Planung, Umsetzung, Prüfung und Integration liefen über orchestrierte KI-Coding-Agenten unter menschlicher Steuerung.

Orchestrator

Claude Code

Claude Code (Anthropic) plant, zerlegt Aufträge in Work Packages, verifiziert Ergebnisse unabhängig, integriert und merged. Merge und Deploy nur nach menschlicher Freigabe.

Worker-Lanes

Sechs Agenten

OpenAI Codex, Cursor Agent, Google Antigravity (Gemini), Grok Build, MiniMax über OpenCode, Cline. Unabhängige Cross-Vendor-Reviews (Cursor, Gemini, Grok) und Open Code Review vor jedem Merge.

Isolation

Worktrees & Branches

Jedes Work Package läuft in einem eigenen Git-Worktree und Branch. Worker committen; pushen, mergen und deployen nie.

Gates

Rund 1 900 Tests

pytest-Suite mit über 4 800 Testfällen im Vollgate (PostgreSQL, Redis), Ruff, Mypy, Playwright-Browser-Gates bei 390/1440/1920/3840 px, SHA-256-Manifest, GitNexus-Impact-Analyse.

Regeln: Ein gemeinsamer Ausführungsvertrag für alle Tools, AGENTS.md als Single Source of Truth, Work-Package-JSONs mit Dateibesitz und Routing-Belegen.

Zahlen: 860 Commits auf main (Stand 13.09.2026) unter dem gemeinsamen Git-Benutzer agent; produktiv seit 2. September 2026. Menübilder sind KI-generierte Serviervorschläge (so auch in der App beschriftet).

Mensch: Auftrag, Priorisierung, Freigaben und fachliche Abnahme bleiben beim Menschen; die fachliche Abnahme ist laut README noch offen.

Kanaltrennung als Grundprinzip

Ein System, zwei klare Raster

Jedes Profil hat eigene Regeln, Revisionen und öffentliche Ansichten. Entwürfe bleiben intern.

01 / Patienten

Die ganze Woche im Blick

Montag bis Sonntag, Mittag und Abend, jeweils Menü 1 und vegetarische Auswahl.

  • Web-, Mobile- und Druckansicht
  • Tages- und Wochen-Signage
  • Kanal technisch ohne Kostenfelder

02 / Cafeteria

Fokussiert auf den Mittag

Montag bis Freitag mit zwei Menüarten und getrennten Ansätzen für Mitarbeitende und externe Gäste.

  • Samstag und Sonntag geschlossen
  • Eigene Publikation und Datenquelle
  • Kein Rückgriff auf Patientengerichte

Schnittstellen

REST, FHIR und MCP — drei Zugänge zu denselben publizierten Speiseplänen.

01

REST API v1

OpenAPI 3.1 unter /api/v1/openapi.json, Swagger UI unter /api/v1/docs. API-Schlüssel werden unter /admin/api verwaltet.

02

FHIR R5

Lesezugriff über /fhir/metadata, Ressourcen NutritionProduct und Composition.

03

MCP-Server

Stdio-basiert für LLM-Clients, Quelle unter reference_scaffold/dishboard_mcp/.

Druck & CSV — A4-Wochenpläne unter /druck/patienten/woche und /druck/cafeteria/woche, CSV-Import/Export mit Validator unter /admin/import und /admin/export/<profile>.csv.

Solider, überschaubarer Stack

Für den Küchenalltag gebaut

01

Flask

Serverseitige Ansichten und einfache Küchenraster statt unnötiger CMS-Komplexität.

02

PostgreSQL

Profilregeln, Mahlzeiten und Publikationen werden bereits in der Datenbank abgesichert.

03

Lokale Konten + Entra

Projektumfang für lokale Zugänge sowie Microsoft Entra ID mit rollenbasierter Küchenfreigabe.

04

Unabhängige Revisionen

Tag und Woche eines Profils stammen aus derselben Publikation; das andere Profil bleibt unberührt.

05

Docker Compose + Healthchecks

Deployment über docker compose, Liveness unter /health/live, Readiness unter /health/ready.

06

Rollen: Editor · Publisher · Admin

Drei Entra-App-Rollen regeln Bearbeitung, Freigabe und Systemzugang getrennt pro Kanal.
